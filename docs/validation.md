The numerical trace was generated by compiling the original ROS1 core independently with only

It does not use the ported core to produce its own expected outputs.

The native GELLO test uses a zero-pose software fixture with collision checks disabled and mock
state for devices outside the selected arm. This isolates message and lifecycle integration;
the normal user launch retains collision checks. The mock hardware is not a validated dynamics
or contact simulator. The dual test separately checks both controller managers/claims.

## Changes that affect comparison with ROS1

- TORQUE firmware replaces the old CURRENT conversion path. Gains and contact response need
  commissioning. A lower-stiffness candidate profile is supplied.
- Gravity is added in the controller using the shared model, rather than in `kortex_hardware`.
- Feedback/output filter coefficients are preserved but now owned by the controller. Driver
  URDF torque limits and Exclaim's slew limiter differ from old current-limit placement.
- Native ROS2 GELLO's existing 100 Hz / 25 ms position-only input replaces the old ROS1
  20 Hz / 100 ms quintic input. It is deliberately not retimed by this port.
- Lifecycle restart and continuous-reference handling are fixed. Invalid numerical state now
  requests controller deactivation/driver hold rather than emitting zero total torque.
- The maximum-integrated-error dimension typo is fixed; integral action remains disabled in
  the initial profile.

## Still requiring the robot

Actual SDK entry/exit, failed mode-switch recovery, torque-command signs (including lightly
loaded axes), physical soft-stop/USB behaviour, firmware compatibility, fault and communication
recovery, payload/model accuracy, loop timing/feedback age, tracking and contact behaviour,
manual guiding and reactivation are not hardware-qualified by these tests.

GCC's LTO jobserver failed under amd64 emulation when building the existing native IK Python
module. Disabling interprocedural optimization resolved that build failure; the validation recipe
records the flag. The VM cannot establish a 1 kHz real-time deadline. On-robot acceptance and
measured timing belong to the control NUC procedure in `commissioning.md`.

## FollowJointTrajectory / MoveIt workflow follow-up

The restored action server was tested with real ROS action clients against the loaded compliant
effort plugin: completion/feedback, malformed goal rejection, reordered joint names, cancellation,
action preemption, path/goal tolerance aborts, topic ownership and controller deactivation. A real
`move_group` process in `mode:=compliant` successfully executed a zero-motion trajectory through
the compliant action while the position controller was inactive. This proves execution routing;
the effort mock does not simulate physical tracking, and the test does not collision-check a
calibration movement. Existing controller, arm bringup, MoveIt configuration, GELLO delivery and
two-manager tests passed. Both hand configurations preserve non-arm MoveIt controller entries.

The trial operator Procman config uses a shared `arm_mode` option (default `position`) for the
arm launch, MoveIt execution and GELLO routing. Its configuration parses with the native Procman
parser. Selecting `compliant` loads the arm compliant controllers inactive; activation remains
explicit. The validation Docker recipe includes the MoveIt runtime/controller-manager plugins
needed for the execution test.

## Read-only gravity monitor follow-up

The monitor was loaded into both existing arm managers alongside active POSITION trajectory
controllers for Tesollo and Robotiq mock models. Tests verified zero claimed command interfaces,
retained POSITION ownership, successful rigid motion during monitoring, numerical agreement with
an independent full-model gravity calculation at sampled poses, and successful rigid motion after
monitor unloading. The shared gravity function remains covered by the original numerical trace.
A lifecycle test supplies only state interfaces in a reordered layout and checks invalid samples
remain diagnostic-only. Model comparison does not claim physical dynamics/torque-sign validation.
The temporary Procman menu includes loading, plots, settled-sample indicators and recording.

## Fault-recovery follow-up — 24 November 2026

The driver now latches faults observed during torque control, including base fault/servoing-ready
states and either actuator fault bank. Externally clearing a fault cannot resume old effort
commands. Recovery verifies POSITION and seeds the measured pose before sending another cyclic
frame; an explicit successful full-arm POSITION controller switch is required before torque can
be activated again. Explicit fault reset and soft-stop release preserve that latch. Failed
restoration requests an emergency stop and reports an error.

Jazzy/Ubuntu 24.04 amd64 Docker build and driver tests passed: **21 effort/recovery GTests**
(the existing five plus 16 new cases) and **14 existing soft-stop GTests**. Colcon reports
37 passing entries including the two CTest wrappers, with no failures or skips. The recovery
tests exercise production read/write, mode prepare/perform, torque entry/exit and command building
with simulated SDK operations. They cover external clear with stale commands and a changed pose,
all live fault sources, explicit POSITION/restart, late faults, failed mode/frame restoration,
fault reset and soft-stop interaction. They also verify POSITION faults do not acquire a torque
latch. No physical SDK/firmware or timing qualification is implied; the supported-arm recovery
checks in `commissioning.md` still require the robot.
